# UCSPECの仕様作成と未網羅レビュー

顧客と接点を持つ開発者が、利用者の目的、期待する結果、必要な設計判断を仕様に残せるよう支援する。既知の要求に基づく提案・編集は進め、目的や期待結果など判断に必要な情報が不足する場合だけ質問する。自然言語による業務判断を機械的に合格・承認済みとしない。

## 作業対象と資料

対象のプロジェクトルートと `project.json` を依頼または既存構成から特定する。UCSPEC本体のソースと、UCSPECで仕様を管理するプロダクトを区別する。

- 本体リポジトリでは [docs/authoring.md](../../../docs/authoring.md) と [docs/user-manual.md](../../../docs/user-manual.md) を読む。
- `init` で導入したプロダクトでは [spec/AUTHORING.md](../../../spec/AUTHORING.md) と [spec/USER-GUIDE.md](../../../spec/USER-GUIDE.md) を読む。
- ファイルの存在と対象構成に合う方を選び、対象の `project.json` とその `files` が参照する仕様を読む。サンプル固有の画面遷移や業務ルールを他のプロダクトへ強制しない。

生成HTMLではなく構造化仕様を編集する。共有モデルの状態・イベント・ディシジョンをユースケースから参照し、目的ごとにコピーしない。

仕様はデータを持たない。変数、条件式、ガード、イベントの入力を書かず、業務上の結果の違いはディシジョンの名前付き分岐で表す。どの分岐になるかを決める業務の論理とデータの中身は実装とそのテストが受け持つ。権限の違いはイベントの `actors` で表す。子状態は親のイベントを引き継ぎ、末端に近い状態の同名イベントが上書きする。行き先（`to` / `decision`）を持たないイベントや分岐は状態に留まる。ユースケースの `package` は分類であり、`scope` の代わりにはしない。`commonRules` はシステムエラー処理などの共通方針を人に伝える文章であり、検査で実装を保証するものと混同しない。

## 目的とシナリオを記述する

アクター、達成したい目的、開始する状態、達成・中止・拒否などの終わり方を整理してユースケースを記述する。`scope` はその目的に必要なイベントから、`ends` は目的が終わる遷移（`状態:イベント` または `状態:イベント>分岐`）から定義し、登録済みシナリオの列から逆算しない。

各シナリオには `goal` と `expectedOutcome` を必ず記述する。`goal` はそのシナリオで確かめたい利用者の目的、`expectedOutcome` は人が理解できる業務上の結果とする。成功経路だけでなく、既知の要求にある入力不備・拒否・失敗・中止・再試行を扱う。

`start` と、イベント名 `event` と通る分岐名 `branches` の `steps` を定める。`expectedOutcome` の文章は機械検証されない。シナリオが成立しても、手順が状態の構造の上でたどれることを示すだけで、保存の永続性や外部処理、実アプリの正しさまで保証されたとは報告しない。ユースケースの `ends` を通った後に続く操作は、通常シナリオに継ぎ足さず、`actor` を持つ横断回帰の `regressions` として扱う。アクターが起こせないことの確認は、回帰の `reject` 手順で表す。

## 検査して未網羅を評価する

導入先ではプロダクトルートから、固定版を使うランチャーで検査する。

```powershell
.\scripts\ucspec.ps1 check
.\scripts\ucspec.ps1 build
```

本体ソースを変更している場合はソースから実行し、対象の `--project` を明示する。以下は本体サンプルの例であり、別の仕様をレビューする場合はそのパスを使う。

```powershell
$env:GOPROXY = 'off'
$env:GOTOOLCHAIN = 'local'
go run -mod=readonly ./cmd/ucspec check --project examples/customer-crud/spec/project.json
go run -mod=readonly ./cmd/ucspec build --project examples/customer-crud/spec/project.json
```

依存が不足した場合は未実行として報告する。仕様の分析中にネットワーク取得やツールの更新を始めない。設定した環境変数は作業後に元へ戻す。

出力先の `report.json` とHTMLを読み、構造エラー、不成立のシナリオ、完了できないユースケース開始、到達できない状態・遷移の警告、解析の完了状態、各指標の不足を確認する。探索未完了を証明成功と扱わず、不成立シナリオを網羅済みに数えない。

未網羅の意味は指標ごとに評価する。

| 指標 | 評価する内容 |
|---|---|
| `states` | 未到達の末端状態ごとに、その利用状況や結果を確認するシナリオが必要か評価する。 |
| `compositeStates` | 未到達の複合状態ごとに、そのまとまりを利用する目的を確認する。親に到達しても未通過の子が網羅済みとは扱わない。 |
| `transitions` | 不足するイベント・分岐ごとに、利用者に必要な操作・結果がシナリオから抜けていないか確認する。 |
| `pairs` | 直前の操作履歴によって次の操作の意味・結果が変わるか確認する。 |
| `primePaths` | 異なる利用者目的や結果を表す経路が漏れていないか確認する。 |
| `boundedPaths` | 探索された全件を個別管理することを目標にせず、回数・順序の違いに業務上の意味があるか確認する。 |

反復を既存シナリオで代表させるなら、回数非依存、冪等性、再試行時の入力保持など、その判断が成立する前提を具体的な設計要求として残す。現在の検査や代表シナリオだけで、その前提の実装や任意回数の反復まで保証されたとしない。

## レビューを記録する

対象ユースケースの `coverageReviews` に、レビューIDをキーとするオブジェクトを追加する。現行レポートの `usecases` から対象IDの結果を選び、指標の `missing` にある要求IDを転記する。要求IDやハッシュを推測しない。

| フィールド | 記録する内容 |
|---|---|
| `kind` | 上記6指標のいずれか。 |
| `requirements` | 同じ指標に属する未網羅要求IDの配列。まとめる場合は共通の判断根拠を示す。 |
| `status` | `addScenario`、`represented`、`forbidden` のいずれか。 |
| `reason` | その扱いにする業務上の根拠。 |
| `scenario` | `represented` の場合に必須。同じユースケース内の代表シナリオID。 |
| `architectureRequirements` | 判断から導く設計要求を平文の文字列配列で記録する。保証済みの性質と混同しない。 |
| `basisHash` | 対象ユースケースのレポートにある現在の `reviewBasisHash`。 |

- `addScenario`: 必要な目的・結果が不足しているためシナリオを追加する判断。経路の生成だけで業務要求が確認されたとみなさない。
- `represented`: 既存シナリオが業務上の意味を代表する判断。対象経路との違い、代表できる理由、成立に必要な設計要求を記録する。これは経路包含の機械的な証明ではない。
- `forbidden`: 業務上禁止すべき経路という判断。状態の構造、イベントのアクター、拒否回帰などへ反映する内容を明らかにする。記録だけで禁止が実現したとみなさない。

`reviewBasisHash` はプロジェクト設定、共有モデル全体、回帰と共通ルール全体、対象ユースケースのシナリオを含む定義（`coverageReviews` を除く）と `toolVersion` に依存する。他のユースケースの定義とレビュー記録自体は対象外とする。これらの検証条件やCLIの版が変わった後は再検査し、古い根拠による `stale` なレビューを再評価する。警告を消すために `basisHash` だけを無検討で更新しない。

レビューの記録は網羅率の分子・分母や閾値を変更しない。未網羅を代表・禁止と判断しただけで生の網羅率が上がったとは扱わず、閾値、回帰、`scope`、`ends` を緩めて通さない。

編集後に `check` と `build` を再実行し、追加した目的・期待結果、未網羅の扱いと設計要求、古くなったレビュー、検査結果と未検証事項を報告する。実装テスト基盤への連携や合意管理の仕組みは、このスキルの作業に含めない。
