# 構造化仕様の記述ガイド

状態定義の要素と関係は、ucspecリポジトリの [状態定義モデル](model.html)（`docs/model.html`）にクラス図でまとめています。このガイドは、各要素の書き方と検査の範囲を説明します。

## 正本とファイル

`spec/project.json` と、その `files` から読み込むファイルが正本です。入力はJSONまたはYAMLです。テンプレートは、人とAIの差分確認や曖昧な型変換を避けるためJSONを使用します。YAMLの複数ドキュメント、アンカー/エイリアス、マージキー、非文字列キーは拒否します。JSON/YAMLとも同じキーの重複、未知の構造フィールド、同じ定義の再定義を拒否します。

各ファイルには `"schemaVersion":"1"` を付けます。`$schema` フィールドは入力形式に含めません。エディターの設定から同梱の `spec/ucspec.schema.json` を関連付けてください。ファイルパターンはspec相対の通常globです。`**` による再帰globはありません。必要なパターンを明示します。

診断の位置は相対ファイル名とJSON Pointerです。YAMLパースエラーの一部は行番号も示しますが、全診断を行番号へ対応付ける機能ではありません。

## プロジェクト設定

```json
{
  "schemaVersion": "1",
  "name": "顧客管理",
  "repository": "nuitsjp/ucspec",
  "files": ["model/*.json", "usecases/*.json", "checks/*.json"],
  "output": "artifacts/ucspec",
  "limits": {"steps": 10, "paths": 100000},
  "coverage": {"transitions": 100}
}
```

`limits.steps` は上限付き完了パスの最大遷移数（既定12、1〜256）、`limits.paths` は探索する構成数と経路探索の作業量の上限（既定100000、1〜2000000）です。システムの開始は `project.json` ではなく、状態定義ファイルの最上位に書く `start` で表します。

`coverage` のキーは `states`, `compositeStates`, `transitions`, `pairs`, `primePaths`, `boundedPaths` です。指定した指標のみ閾値をCI判定に使います。未指定指標も計算・表示します。解析未完了は指標の閾値指定にかかわらず不合格です。

## 名前と参照

アクター、状態、イベント、分岐は名前そのものが識別子です。日本語を使えます。名前には `/` `:` `>` `?` `[` `]` を含められず、前後に空白を置けません。製品のCLIは、同じ並び（同じ親の子状態、同じ状態のイベント、同じディシジョンの分岐、アクター）の中で、NFKC正規化すると同じになる名前（全角・半角の違いなど）を表記ゆれとして拒否します。

ユースケース、シナリオ、回帰、パッケージ、共通ルール、評価記録のIDは、英字で始まる英数字・`_`・`.`・`-` です。

状態はルート状態からのパス（例: `顧客管理/顧客編集`）で識別します。状態を参照する箇所には、完全なパスか、一つの状態だけに一致するパスの末尾（例: `顧客編集`）を書けます。複数の状態に一致する末尾は曖昧としてエラーになるため、パスをさらに書き足します。

遷移は次の形で参照します。レポート、図の詳細、網羅率の項目IDも同じ形です。

| 遷移 | 形 | 例 |
|---|---|---|
| イベント | `状態:イベント` | `顧客管理/顧客編集:更新` |
| 分岐 | `状態:イベント>分岐`（分岐が続く場合は `>分岐` を重ねる） | `顧客管理/顧客編集:更新>顧客なし` |
| 開始 | `状態:[開始]` | `顧客管理:[開始]` |
| ルート状態の開始・イベント | 状態の部分を空にする | `:[開始]` |

## 状態定義

### ルート状態

状態定義ファイルの最上位は、名前のないルート状態です。最上位に書く `start`、`events`、`states` はルート状態に属します。複数のファイルは一つのルート状態にまとまります。ルート状態の `start` がシステム全体の開始で、全ファイルを通じてちょうど一つ書きます。最上位の状態名や最上位のイベント名を複数のファイルで重複して定義することはできません。

ルート状態に書いたイベントは、すべての状態で有効です。

### アクター

`actors` は最上位（どのファイルでもよい）に、名前から任意の `description` へのmapとして定義します。イベントの `actors` とユースケースの `actor` は、アクターを名前で参照します。利用者の役割や権限の違いは、イベントを起こせるアクターで表します。

### 状態

状態は親の `states` の中に入れ子で書きます。名前は同じ親の中で一意です。

| 属性 | 内容 |
|---|---|
| `screen` | 任意。表示する画面の名前。図には状態名と異なるときだけ表示します |
| `layoutLayer` | 任意の非負整数。同じ親の中での配置順（図の表示専用） |
| `start` | 子状態を持つ状態では必須。子状態を持たない状態には書けません |
| `events` | この状態で起こせるイベント |
| `states` | 子状態 |

子状態を持つ状態は複合状態です。複合状態へ入ると、その `start` をたどって子状態を持たない状態（末端状態）まで進みます。状態に入っている間、末端状態とその親（祖先）がすべて有効です。並行領域、履歴状態、入場・退場アクションは扱いません。複合状態へ戻る遷移は、前回の子状態ではなく `start` から入り直します。

同一画面内の編集中/確認中などは別状態として定義できます。同じ論理画面をユースケースごとに複製しません。

### 遷移（イベント・開始・分岐）

イベント、開始、分岐はどれも遷移です。遷移は任意の `action` と、行き先として `to`（状態の参照）または `decision`（ディシジョン）のどちらか一方を持ちます。両方を書くことはできません。

- `to` を持つ遷移は、その状態へ入ります。複合状態なら `start` をたどります。
- `decision` を持つ遷移は、ディシジョンで分岐します。
- どちらも持たない遷移は、イベントが起きた時点の末端状態に留まります。退場・再入場や `start` への入り直しは起こりません。

`action` は選んだ遷移で行うシステムの振る舞いで、「顧客を更新する」のように「○○を○○する」の形で簡潔に書きます。イベントを受け付けるだけでシステムの振る舞いがない遷移では省略できます。

### イベント

イベントは状態の `events` に、イベント名をキーとして書きます。イベントは遷移そのものです。別途の遷移定義や遷移IDはありません。

| 属性 | 内容 |
|---|---|
| `actors` | 必須。このイベントを起こせるアクター（1つ以上） |
| `action` | 任意。システムの振る舞い |
| `to` / `decision` | 任意。どちらか一方。どちらもなければ留まる |
| `defaultVisible` | 任意。`true` なら通常図に表示します（検査には影響しません） |

イベント名は「更新」「検索へ戻る」のような短い語句にします。利用者の操作、時間経過、外部処理の応答などの契機を、主語を付けずに表します。

子状態は親のイベントを引き継ぎます。有効な末端状態がどこであっても、その祖先のイベントは起こせます。同じ名前のイベントを末端に近い状態でも定義すると、近い方が親のイベントを上書きします。上書きされて、到達できるどの状態からも起きない親のイベントは警告になります。

```json
{
  "states": {
    "顧客管理": {
      "start": {"to": "顧客検索"},
      "events": {
        "設定を選択": {"actors": ["担当者"], "action": "通知設定を表示する", "to": "設定"}
      },
      "states": {
        "顧客検索": {
          "events": {
            "閲覧": {
              "actors": ["担当者"],
              "defaultVisible": true,
              "decision": {
                "label": "顧客の有無",
                "branches": {
                  "顧客あり": {"action": "顧客を表示する", "to": "顧客閲覧"},
                  "顧客なし": {"action": "アラートを表示する"}
                }
              }
            }
          }
        },
        "顧客閲覧": {}
      }
    }
  }
}
```

これは抜粋です。アクター `担当者` と状態 `設定` の定義は別途必要です。「設定を選択」は顧客管理の中のどの子状態からでも起こせます。「顧客なし」は行き先を持たないため、閲覧を起こした顧客検索に留まります。

### 開始

開始は、状態へ入ったときに最初に進む遷移です。行き先の状態かディシジョンを必ず持ち、留まることはできません。開始の直後に分岐する場合は、開始に `decision` を書きます。開始とその分岐の行き先は、その複合状態の内側の状態でなければなりません。ルート状態の開始だけは、どの状態を行き先にしてもかまいません。

```json
{
  "schemaVersion": "1",
  "start": {"to": "顧客管理"}
}
```

開始は利用者が起こすイベントではありません。状態へ入ると自動的に進みます。開始の遷移自体はシナリオの手順や網羅率に現れませんが、開始のディシジョンの分岐は経路と網羅率に現れます。

### ディシジョン

ディシジョンは、遷移の後にどの分岐へ進むかを表します。独自の名前や識別子を持たず、それを持つイベント・開始・分岐に属します。

| 属性 | 内容 |
|---|---|
| `label` | 任意。図に表示する名前。重複してかまいません |
| `branches` | 必須。分岐名から遷移（`action`、`to` または `decision`）へのmap。2つ以上 |

分岐は条件式を持たず、名前だけを持ちます。どの分岐を通るかはシナリオが分岐名で指定します。分岐の後にさらに分岐する場合は、分岐に `decision` を入れ子で書きます。分岐が合流したり循環したりすることはありません。行き先を持たない分岐は、イベントが起きた末端状態へ戻ります。

```json
"branches": {
  "顧客なし": {"action": "アラートを表示する", "to": "顧客検索"},
  "顧客あり": {
    "decision": {
      "label": "競合の有無",
      "branches": {
        "競合なし": {"action": "顧客を表示する", "to": "顧客閲覧"},
        "競合あり": {"action": "競合を表示する", "to": "顧客編集"}
      }
    }
  }
}
```

この形式はデータを持ちません。変数、条件式、イベントの入力、ガードはありません。顧客が存在するかがどう決まるかなどのデータの中身と業務の論理は検査の対象外で、実装とそのテストが受け持ちます。

## 図の表示

図はイベントを「イベント名」と「/ アクション」の行で、分岐を「[分岐名]」と「/ アクション」の行で表示します。ディシジョンは菱形で、それを持つ遷移の矢印が菱形へ入ります。行き先を持たないイベントは状態の枠内に行として表示し、行き先を持たない分岐はイベントを起こした状態へ戻る矢印で表示します。複合状態の枠内の黒丸はその状態の開始を、図の外側の黒丸は全体図ではルート状態の開始の行き先、ユースケース別図ではそのユースケースの `starts` を指します。

`defaultVisible` は検査の入力ではなく、図の表示集合を決める属性です。`true` なら通常図のレイアウトへ含め、未指定または `false` なら通常図のレイアウトから除外します。イベントの分岐はイベントの表示に従います。シナリオ、未網羅候補で選択した経路は属性に関係なく通常表示の集合へ加わり、「全遷移を表示」では全遷移を配置します。表示集合が変わるとelk-goが状態の位置、複合状態の枠高さ、図幅を再計算します。非表示のイベント行は通常図の枠高さに含めません。この属性は実行、`scope`、網羅率を変えません。

全体図、ユースケース別図、複合状態の枠内は、共通のELK設定で上から下（`DOWN`）へ自動配置し、`NETWORK_SIMPLEX`をノード配置方式に使います。状態の任意属性 `layoutLayer` は同じ親の中での配置順だけを指定し、非負整数の小さい層を上に、同じ層を同じ配置帯にします。異なる層の順序は保証され、同じ層の帯内の上下・横配置は自動です。同じY座標や横一列は保証しません。未指定の状態とディシジョンは自動配置に任せます。図の外側の黒丸は各図の最上段・左右中央に固定し、複数の開始状態がある場合は開始記号の列全体を中央に並べます。`layoutLayer` はピクセル位置や層の高さを指定するものではありません。

## 共通ルール

DB、通信、実メール送信などのシステムエラー処理は、状態や分岐を増やさず、Documentのルートに共通ルールとして記述します。`commonRules` はIDから `name` と `description` へのmapです。HTMLでは「共通ルール」へ表示されます。

```json
{
  "schemaVersion": "1",
  "commonRules": {
    "systemError": {
      "name": "システムエラー",
      "description": "システムエラー時は共通メッセージを表示し、編集入力を保持する。更新・削除の確定は原子的に行い、失敗時は直前の確定データを維持する。"
    }
  }
}
```

共通ルールは実装方針を共有する文章です。検査は、共通メッセージの表示、入力保持、原子的な確定などの実装を保証しません。業務上の結果の違いだけを状態・イベント・分岐へ抽象化し、DBの内部状態や進捗表示を状態として追加しないでください。

## ユースケースとシナリオ

`usecases` の各項目に、`name`、`goal`、`actor`、`starts`、`ends`、`scope`、`scenarios` を定義します。任意の `package` で所属するユースケースパッケージのIDを指定します。

| 属性 | 内容 |
|---|---|
| `actor` | ユースケースのアクター。シナリオはこのアクターとして操作します |
| `starts` | 開始する状態の参照。システムの開始から到達できなければなりません |
| `ends` | 終了とする遷移の参照（`状態:イベント` または `状態:イベント>分岐`）。いずれかを通ると、ユースケースは終わります |
| `scope` | ユースケースが扱うイベントの参照。その下の分岐は自動的に含みます |

`scope` のイベントは、ユースケースのアクターが起こせなければなりません。`ends` に書くイベントとイベントの分岐は、`scope` のイベントに属さなければなりません。ディシジョンを持つイベントを `ends` に書くと、どの分岐を通っても、分岐を終えて状態に戻った時点で終わります。特定の分岐だけを終了にする場合は、分岐まで書きます。成功、中止、拒否を終了に含めることもできます。

`scope` はその目的の検査範囲を定義する項目です。シナリオ列から自動生成しません。これにより登録シナリオの書き漏れを分母から消しません。ただし、人が `scope` から本来必要なイベントを除いた誤りまで推測できるわけではありません。

パッケージは `usecasePackages` で定義し、`name` と任意の `parent` を持ちます。親を省略するとルートになります。同じパッケージに子パッケージとユースケースを置けます。親の不存在、自己参照、循環、存在しないパッケージへの所属はエラーです。`package` 未指定のユースケースはルートに表示します。

```json
{
  "schemaVersion": "1",
  "usecasePackages": {
    "operations": {"name": "運用設定"},
    "notifications": {"name": "通知設定", "parent": "operations"}
  }
}
```

パッケージは整理単位です。所属やネストによって `scope`、開始・終了、網羅率の分母は変わりません。パッケージ名や親の変更は、所属するユースケースへの変更影響に記録します。

### シナリオ

各シナリオ（回帰を含む）には `name`、`goal`、`expectedOutcome`、`start`、`steps` を記述します。`goal` は利用者が何のために実施するか、`expectedOutcome` はその目的に対して何が成立して終わるかです。完了画面の表示だけを期待結果にせず、保存された内容、取消時に維持される情報、権限によって保護される情報などを書きます。失敗・中止・拒否も、その場合の結果を明示します。

`start` は開始する状態の参照で、ユースケースのシナリオでは `starts` のいずれかです。各手順 `steps` は、起こすイベント名 `event` と、その後に通る分岐名の並び `branches` で書きます。イベントは、その時点の末端状態で有効なもの（祖先から引き継いだものを含む）から名前で選びます。任意の `note` に補足を書けます。

```json
{
  "update": {
    "name": "正常に更新する",
    "goal": "顧客情報を最新の内容へ編集して更新する",
    "expectedOutcome": "顧客情報が更新され、顧客閲覧画面で更新結果を確認できる",
    "start": "顧客閲覧",
    "steps": [
      {"event": "編集"},
      {"event": "更新", "branches": ["顧客あり"]}
    ]
  }
}
```

これは `scenarios` 内の抜粋です。ユースケースのシナリオは、次をすべて満たすと成立します。

- 各手順のイベントがその時点で有効で、ユースケースのアクターが起こせる。
- 手順が通るディシジョンごとに、実在する分岐名を順に指定している（過不足なし）。
- 手順のイベントが `scope` に含まれる。
- `ends` のいずれかを通り、その手順でシナリオが終わる。終了後に手順を続けることはできません。

ユースケースのシナリオに `actor` は書きません。ユースケース横断の継続操作は回帰に記述します。不成立シナリオは網羅済みに数えません。

`expectedOutcome` は人が読む文章で、検査はその内容を確かめません。シナリオの成立は、手順が状態の構造の上でたどれることだけを示します。文章の正しさ、実データの永続化、モデルと実装の一致はこの検査では保証しません。HTMLでは目的と期待結果を操作列より先に表示します。

## 回帰

`regressions` は通常シナリオと同形式で、ユースケースの `scope` と `ends` に束縛されない横断経路です。回帰には `actor` が必須です。回帰は定義網羅率へ加算せず、独立した合否として表示します。

`{"event": "編集", "reject": true}` は、その時点でアクターがそのイベントを起こせないこと（イベントが有効でない、またはアクターに許されていない）を確認し、状態を変えません。権限は、イベントを起こせるアクターで表します。拒否の手順には分岐を書けず、ユースケースのシナリオには書けません。これは否定テストであり、実装のイベントを実行した意味ではありません。

## 検査で確かめること

- 構造: 名前の規則、参照先の存在と一意性、子状態を持つ状態の開始、遷移の行き先、ディシジョンの分岐数、ユースケースの `scope` と `ends` とアクターの整合。
- シナリオ: ユースケースのシナリオと回帰が、状態の構造の上でたどれること。
- 完了可能性: ユースケースの各開始から、`scope` のイベントだけで `ends` に到達する経路があること。
- 到達性: ルート状態の開始から到達できない状態と、到達できる状態から一度も起きない遷移（上書きされた親のイベントなど）を警告します。ユースケースの開始が到達できない場合はエラーです。
- 網羅率: 末端状態、複合状態、遷移、連続2遷移、プライムパス、上限付き完了パスをシナリオがどれだけ通っているか。

データの中身と業務の論理は検査しません。それは実装とそのテストが受け持ちます。

## 変更レビュー

### 未網羅項目の評価記録

ユースケースの任意の `coverageReviews` に、未網羅項目を評価した記録を保存できます。一つの記録の `requirements` に複数の項目を指定して、同じ業務ルール・設計要求としてまとめられます。対象は同じ指標内に限ります。

`kind` は `states`、`compositeStates`、`transitions`、`pairs`、`primePaths`、`boundedPaths` の6指標から選びます。末端状態と複合状態は別に評価し、親への到達だけで未通過の子を確認済みとしません。ディシジョンは状態網羅の対象には加えず、その分岐を遷移・経路の指標で評価します。

```json
{
  "coverageReviews": {
    "repeatedNotificationEdit": {
      "kind": "boundedPaths",
      "requirements": ["report.jsonのmissingにあるIDを転記"],
      "status": "represented",
      "reason": "通知設定を複数回更新する経路は、一度更新するupdateシナリオで代表させる",
      "scenario": "update",
      "architectureRequirements": [
        "更新の回数によらず、最後に更新した内容を通知設定へ反映する"
      ],
      "basisHash": "report.jsonの対象usecaseのreviewBasisHashを転記"
    }
  }
}
```

これは形式の説明であり、代表判断を承認済みとするものではありません。IDとハッシュのプレースホルダーをそのまま入力しないでください。`check` または `build` 後のreport.jsonで、対象ユースケースの `coverage[].missing[].id` と `reviewBasisHash` を取得します。HTMLでも「評価記録を編集するための情報」を確認できます。

| status | 意味 |
|---|---|
| `addScenario` | 追加の目的・期待結果があり、シナリオ追加が必要 |
| `represented` | 指定した既存シナリオで確認観点を代表させる。`scenario` に同じユースケース内のシナリオIDを必須指定 |
| `forbidden` | 起きてはいけない振る舞いとして、モデル・設計の修正が必要 |

`kind`、一つ以上の `requirements`、`status`、空でない `reason`、`basisHash` は必須です。`architectureRequirements` は参照IDではなく設計への要求を記述する文章の配列です。同じ指標・項目を複数の記録へ重複登録しません。現在の評価がない項目は「未評価」として表示され、未決のものを無理に分類する必要はありません。

`represented` は経路を実際に網羅した意味ではありません。評価記録は生の網羅率、閾値、検査の合否を変更しません。設計要求の記録も、それが実装・テストで満たされたという保証ではありません。禁止する判断を記録しただけではモデルから経路は消えません。

`reviewBasisHash` はプロジェクト設定、共有モデル・検査定義、対象ユースケース（シナリオを含む）、ツール版を元に計算し、評価記録自身は除きます。仕様・設定・版が変わった記録、対象が現在の未網羅項目にない記録、代表シナリオが成立しない記録、解析が未完了の記録は `stale`（再評価が必要）になります。出力先などの設定変更でも保守的に再評価を求める場合があります。古い記録は隠さず表示します。ハッシュだけを機械的に更新せず、経路・期待結果・設計要求を見直してから記録を更新または整理してください。

### 変更影響の限界

変更影響は再確認の候補です。定義の差分、依存関係、シナリオの成立性は自動で調べられますが、目的や期待結果の文章の意味が変わったか、顧客への再確認が必要かは開発者が判断します。顧客との合意状態の管理やE2Eテスト結果との連携は対象外です。

`scope` や `ends` を変える、閾値を下げる、回帰を外すだけで検査を通さないでください。候補の理由・期待結果と共に人の判断を残します。共通ルールの変更は、取りこぼしを避けるため全ユースケースへの保守的な影響として表示されます。

この形式の機械検査は状態の構造とシナリオの整合性を強めるものです。記述されていない要求、データの中身や業務の論理の不具合、実装との不一致を検出するものではありません。
