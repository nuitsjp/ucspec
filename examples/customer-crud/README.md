# 社内担当者向け顧客管理サンプル

ブラウザーで `app/index.html` を開くと、初期画面の顧客検索から操作を始められます。画面左には「顧客管理」「設定」のメニューを常設しています。顧客管理は検索・閲覧・編集・削除、設定は「顧客情報の更新通知をメールで受け取るか」を同じ画面で編集・更新できます。顧客検索の条件と結果は同じ画面に表示し、検索前・0件・N件を別の画面や状態には分けません。外部サーバー、通信、実メール送信、DB、永続化は使いません。顧客データと通知設定をメモリ上で保持し、リセット/再読込で初期化します。

左メニューの「サンプル操作用」を開くと、閲覧専用の権限、更新/削除の失敗、リセットを試せます。削除した顧客は検索しても復活しません。更新・削除処理中はメニューを移動できず、未更新の入力がある状態で機能を切り替えると破棄確認を表示します。破棄確認を取消した場合は入力を保持します。

この参考アプリは仕様の読み方を学ぶためのものです。CLIがアプリのDOMを操作するテストや、モデルとアプリの自動適合検証は初版に含みません。氏名等の実データはモデルではvalid/invalid、existsなどへ抽象化しています。

## 仕様書

リポジトリルートで:

```powershell
.\dist\ucspec.exe build --project examples/customer-crud/spec/project.json
Start-Process .\examples\customer-crud\artifacts\ucspec\index.html
```

共有モデルはspec/model、目的はspec/usecases、独立したチェックはspec/checksです。顧客管理パッケージの`searchCustomer`（顧客検索）で検索と0件アラートを定義し、閲覧への遷移と閲覧以降は`viewCustomer`で定義しています。設定は通知設定の状態と遷移を同じ画面で扱います。機能間の切り替えと未更新入力の破棄確認は横断回帰シナリオで確認します。

spec/usecases/packages.jsonにパッケージを定義しています。「顧客管理」に検索（`searchCustomer`）・閲覧・編集・削除、「設定」に通知設定の更新が属します。仕様書の左メニューではパッケージ、ユースケース、シナリオを順に開けます。これは仕様の分類であり、アプリ左メニューの機能移動とは用途が異なります。分類を変えても各ユースケースの検査範囲と網羅率は変わりません。

顧客検索は画面`search`で`search`/`open`イベントを受け付ける単一の末端状態です。`searchFound`（顧客あり）と`searchEmpty`（0件）は`search`から`search`へのガード付き内部遷移で、検索状態を離れず一覧表示またはアラート表示を行います。`searched`は検索実行済みだけを記録します。`open.when`は`searched`かつ`exists`（一覧に閲覧対象がある）で、`open`イベントは閲覧時点の存在確認結果を表す有限入力`exists`（`true`/`false`）を持ちます。`openCustomer`は入力値を現在の`exists`へ反映してから`customerAvailability`で判定し、`openView`は顧客ありなら閲覧へ、`openGone`は顧客なしなら検索へ戻って再検索とアラート表示を行います。この入力はユーザーが任意に選ぶ値ではなく、実DBを使わないサンプルで閲覧時の再確認を抽象化したものです。参考アプリの`window.alert`も0件分岐だけで表示します。検索前・0件・N件を別の子状態には分けません。

顧客編集は単一の末端状態`edit`です。編集開始イベント`edit`は`when`で`exists`かつ`canEdit`のときだけ受理し、対象なしまたは権限不足ではイベントを受け付けず、状態と顧客を保持します。`update`イベントは`valid` bool入力を持ち、`when`で有効な入力だけを受理します。入力不備は更新前に拒否し、失敗分岐は描画しません。有効な入力だけが`updateCustomer`で`edit`から`view`へ直接遷移し、`outcome`と`revision`を`updated`にします。顧客閲覧は単一の末端状態`view`です。削除イベント`requestDelete`（ラベル「削除」）は`when`で`exists`かつ`canEdit`のときだけ受理し、対象なしまたは権限不足ではイベントを受け付けず、状態と顧客を保持します。受理後は`confirmed` bool入力で同じイベントを`true`/`false`に分岐し、`true`なら`confirmDelete`（ガードラベル「はい」、アクション「削除」）で`search`へ遷移し、`false`なら`cancelDelete`（ガードラベル「いいえ」、アクション空）で`view`に留まります。`edit`/`requestDelete`の対象なし・権限不足は、`reject:true`を指定した回帰シナリオでイベント非受理と状態・顧客保持を検査します。

図の外部・内部遷移の通常表示は`defaultVisible`で指定します。業務遷移には`true`を明示し、左メニューの機能移動は`false`を明示して通常は非表示にしています。シナリオ・未網羅候補・反例を選択した経路は属性に関係なく表示され、「全遷移を表示」で通常非表示のメニュー遷移も確認できます。表示設定はレイアウト、検査範囲、網羅率を変えません。状態の`layoutLayer`は同じ親内の配置順を指定し、小さい非負整数を上の配置帯に、同じ値を同じ配置帯にします。異なる層の順序は保証され、同じ層の帯内の上下・横配置は自動です。同じY座標や横一列は保証しません。未指定の状態とchoiceも自動配置です。全体図とユースケース図の外側開始黒丸は各図の最上段に置き、その他の最上位の状態・ディシジョンを下へ配置します。複合state内部のinitial、横位置、間隔、矢印は`DOWN`の自動配置に任せます。`layoutLayer`はピクセル位置や層の高さを指定するものではありません。

設定画面は状態と画面が同名の単一の末端状態`notificationSettings`です。下書きの編集は`editNotification`、更新は`updateNotification`、取消は`cancelNotification`で記述し、すべて同じ状態への自己遷移にします。取消時は下書きを確定済みの値へ戻します。通知の成功・失敗結果、進捗、再試行は仕様に含めません。

Documentのルートにある`commonRules`で、DBなどのシステムエラーと進捗表示の共通ルールを記述します。HTMLの「共通ルール」へ表示されますが、有限性質の`properties`とは別の文章であり、モデル検査はシステムエラー処理の実装を保証しません。

シナリオは意図的に全経路を登録せず、未網羅経路と指標の差を確認できるようにしています。閾値設定と残る経路の意味を確認してください。

## 学習用の変更

1. 入力不備の更新を試し、更新前に拒否されることを確認する。
2. `openEdit` のガードを意図的に弱め、閲覧専用ユーザーの回帰ケースが失敗することを確認する。
3. コピーした仕様で削除成功時の`exists`更新を誤ってtrueにし、独立した削除結果の検査で検出する。
4. limits.statesを小さくし、解析未完了が成功扱いにならないことを確認する。

変更前のreport.jsonをbaselineとして保存すると影響比較ができます。元のサンプルを破壊せず、initで作った別ディレクトリやGitブランチで試してください。
