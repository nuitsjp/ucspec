# 利用者マニュアル

## 動作と配布

初版の配布対象はWindows amd64です。配布ZIPをユーザーが書き込めるフォルダーへ展開します。管理者権限、Go、Node.jsは実行時には不要です。Windows on ARM、他OS、コード署名は初版の保証対象ではありません。

この初期ソース一式には検証済み実行ファイルを含めていません。ビルドとRelease作成はREADMEとreleasing.mdを参照してください。

## コマンド一覧

| コマンド | 内容 |
|---|---|
| `help` | 全体ヘルプ |
| `version --json` | 版・スキーマ版・更新元・実行環境 |
| `init` | 各プロダクトの仕様環境を初期化 |
| `check` | 検査してreport.jsonを出力 |
| `build` | 同じ検査を行い、自己完結HTMLを追加出力 |
| `schema --out path` | 同梱JSON Schemaを書き出し |
| `self-update` | 明示的な更新、または更新情報の確認 |

`--help` は各コマンドにも指定できます。引数はフラグ形式です。

## 初期化

```powershell
ucspec.exe init --dir C:\work\product-a --name Product-A --repo nuitsjp/ucspec --dry-run
ucspec.exe init --dir C:\work\product-a --name Product-A --repo nuitsjp/ucspec
```

`--dir` の既定値は現在のディレクトリです。`--name` 省略時はディレクトリ名、`--repo` 省略時はCLIのビルド時に指定した更新元です。`--no-tool` はCLIをコピーしないソース開発用オプションです。

処理前に生成予定ファイルを全件照合します。同じ内容は変更しません。異なる既存内容があれば処理全体を拒否します。失敗時には新規作成したファイルを削除しますが、作成済みの空ディレクトリが残る場合があります。ルートのREADME、AGENTS.md、.gitignoreは変更しません。

初期化は「既存仕様を新形式へマイグレーションする」機能ではありません。別版での再初期化による自動上書きはしません。

プロジェクト用Agent Skillを `.agents/skills/ucspec-authoring/SKILL.md` に配置します。顧客との接点を持つ開発者がユースケース・シナリオの目的と期待結果を記述し、未網羅項目から追加シナリオや設計要求を検討する際に使います。対応するエージェントで `$ucspec-authoring` を指定するか、スキル本文を読み込ませてください。ホーム側のスキルや設定は変更しません。既存の異なるスキルも初期化時の衝突として保護します。

## 検査・仕様書生成

プロダクトのルートで:

```powershell
.\scripts\ucspec.ps1 check
.\scripts\ucspec.ps1 build
Start-Process .\artifacts\ucspec\index.html
```

指定できるオプション:

- `--project spec/project.json`: プロジェクトファイル。YAMLの場合はそのパスを指定します。
- `--out artifacts/review`: 出力ディレクトリを明示的に変更します。
- `--baseline path/to/previous-report.json`: 前回結果と比較し、影響範囲を出力します。
- `--ignore-pin`: 開発時だけ版不一致を明示的に無視します。通常CIでは使用しません。

プロダクトルートはプロジェクトファイルの親ディレクトリのさらに親です。標準の `product/spec/project.json` 配置を使ってください。モデルファイルはspecディレクトリ内に限定し、外へ出るパスや外部へ向くシンボリックリンクを拒否します。

構造化データの読み込みに失敗した場合も診断JSONを残します。buildで読み込み/レイアウトに失敗した場合は、以前の成功HTMLを残さずエラーページを出します。出力ディレクトリ自体へ書き込めない場合はファイルを生成できません。

## HTMLの読み方

全体図と各ユースケースの図は同一モデルから生成されます。ユースケースを選択すると、そのアクター、開始、終了を表示します。シナリオを押すと対応するイベントと分岐が強調表示されます。状態、ディシジョンの菱形、矢印、状態枠内のイベント行を選択すると詳細を表示します。

図の要素は次のとおりです。

- 状態は角丸の枠です。子状態を持つ状態は、枠内に子状態を配置します。状態の `screen` が状態名と異なるときだけ、状態名の下に画面名を表示します。
- イベントの矢印は「イベント名」と「/ アクション」の行を持ちます。行き先を持たない（状態に留まる）イベントは、矢印ではなく状態枠内の行として表示します。
- 菱形はディシジョンで、それを持つ遷移の矢印が菱形へ入ります。菱形から出る矢印は分岐で、「[分岐名]」と「/ アクション」の行を持ちます。行き先を持たない分岐は、イベントを起こした状態へ戻る矢印で表示します。
- 複合状態の枠内の黒丸は、その状態へ入ったときの開始を示します。図の外側の黒丸は、全体図ではルート状態の開始の行き先、ユースケース別図ではそのユースケースの `starts` を指します。開始の矢印は業務の遷移ではないため、網羅率には含めません。

イベントと分岐の通常表示は`defaultVisible`で指定します。`true`のイベントとその分岐は通常図のレイアウトへ含め、未指定または`false`のものは通常図から除外します。シナリオ、未網羅候補を選択した経路は`defaultVisible`に関係なく通常表示の集合へ加わります。図の「全遷移を表示」を切り替えると全遷移を配置できます。表示集合が変わると、elk-goの配置結果に応じて状態の位置、複合状態の枠高さ、図幅が変わります。非表示のイベント行は通常図の枠高さに含めません。選択中の経路は保ったまま、対応する生成済み図へ切り替わります。状態の構造、ユースケースの`scope`、検査や網羅率は変わりません。

左メニューはパッケージ、その配下のユースケース、シナリオの階層です。パッケージはさらにネストでき、各階層を開閉できます。シナリオを選ぶと所属するユースケースの図と網羅率へ切り替わり、その経路を表示します。シナリオ名の検索では、該当項目とその祖先を表示します。回帰シナリオは独立したグループにあり、選ぶと全体図に経路を表示します。

全体図、ユースケース別図、複合状態の枠内は、共通のELK設定で上から下（`DOWN`）へ自動配置し、`NETWORK_SIMPLEX`をノード配置方式に使います。この設定は図全体へ共通に適用し、個別状態の配置属性は追加しません。状態の任意属性`layoutLayer`は同じ親の中での配置順だけを指定し、非負整数の小さい層を上に、同じ層を同じ配置帯にします。異なる層の順序は保証され、同じ層の帯内の上下・横配置は自動です。同じY座標や横一列は保証しません。未指定の状態とディシジョンは自動配置に任せます。図の外側の黒丸は各図の最上段・左右中央に固定し、複数の開始状態がある場合は開始記号の列全体を中央に並べます（個々の記号は重ねません）。その他の最上位の状態・ディシジョンを下へ配置します。複合状態の枠内にある開始の黒丸、横位置、間隔、矢印は自動です。`layoutLayer`はピクセル位置や層の高さを指定するものではありません。

Documentのルートにある`commonRules`は、DBなどのシステムエラーや進捗表示に関する共通ルールをHTMLの「共通ルール」へ表示します。これは人に伝える文章で、検査はシステムエラー処理の実装を保証しません。

シナリオ詳細では、目的と期待結果を操作列より先に読みます。操作列は、各手順の遷移元、イベント・分岐、アクション、遷移先を示します。シナリオの成立は、手順が状態の構造の上でたどれることを示すだけで、自然言語の期待結果や実アプリの動作が検証済みという意味ではありません。

「モデル検査」には、各ユースケースの開始から終了へ到達できるかの検査と、回帰の合否を表示します。「診断」には構造エラー、不成立のシナリオ、到達できない状態・遷移の警告などを表示し、経路を持つ診断はその経路を図に表示できます。

未網羅項目には「未評価」「シナリオ追加が必要」「既存シナリオで代表」「禁止すべき」の評価を表示します。理由・代表シナリオ・設計要求を確認してください。評価を記録しても網羅率は上がりません。仕様変更などで古くなった記録は「再評価が必要」として表示されます。変更影響も再確認の候補であり、文章の意味や顧客への再確認の必要性を自動で決定した結果ではありません。

評価記録を編集するときは、report.jsonの対象usecaseの `reviewBasisHash` と `coverage[].missing[].id` を使用します。HTMLの評価記録用の情報でも現在のハッシュを確認できます。記述ガイドに形式、プロジェクト用スキルに指標ごとの評価方針があります。HTMLは読み取り専用であり、判断を自動保存・承認しません。

各指標の分母、分子、未網羅項目、除外した経路、解析完了状態を確認してください。網羅率の指標は末端状態、複合状態、遷移（イベントと分岐）、遷移ペア、プライムパス、上限付き完了パスの6つです。ユースケースの終了に到達できない経路は「ユースケースの終了に到達できないため除外した経路」として分母とは別に表示します。候補経路は仕様を修正する材料であり、自動的に承認済みシナリオへ登録されません。

HTMLは外部JS/CSS、外部フォント、通信、Node.js、CLIを使わず閲覧できます。CLI生成時に表示集合ごとのSVGを実際のelk-goで配置して埋め込むため、ブラウザーは生成済み図を切り替えるだけで自動レイアウトを行いません。SVGラベルのサイズはフォント非依存の概算であり、実際の日本語フォント次第で余白調整が必要な場合があります。

## 終了コード

| 値 | 意味 |
|---|---|
| 0 | 指定した検査に合格、または操作成功 |
| 1 | 検証違反、閾値未達、解析未完了、dry-runでの衝突 |
| 2 | 引数、ファイルI/O、読み込み、レイアウト、導入/更新処理のエラー |

`verified` は設定した検査への合格です。設定していない指標が100%未満でも合格する場合があります。`incomplete` は探索上限などにより判断しきれていない状態です。表示される%が高くても解析未完了を合格とみなしません。

## 更新: 単独CLI

```powershell
C:\Tools\ucspec\ucspec.exe self-update --check --repo nuitsjp/ucspec
C:\Tools\ucspec\ucspec.exe self-update --version 0.2.0 --repo nuitsjp/ucspec
```

`--version` を省略すると最新の公開済み安定版を選びます。これは明示コマンドを実行したときだけの動作で、定期確認やバックグラウンド更新はありません。`--check` はネットワークで情報を取得しますが、実行ファイルを変更しません。

HTTPSのGitHub APIから対象版のZIPとchecksums.txtを取得し、SHA-256、ZIP構造、Windows amd64 PE、実行ファイルが返す版/スキーマを確認します。既存実行ファイルを `.previous` に移動して置換します。現在のプロセスは旧版のまま正常終了し、次回起動から新版になります。プロダクトの版固定は変更しません。

コード署名はありません。チェックサムは破損を検出しますが、更新元リポジトリやアカウントの侵害を防ぐ仕組みではありません。信頼できる更新元のみ指定してください。

## 更新: プロダクトの固定版

```powershell
# プロダクトルート
.\scripts\ucspec.ps1 self-update --project . --version 0.2.0 --repo nuitsjp/ucspec
.\scripts\ucspec.ps1 build
```

旧版を上書きせず `.tools/ucspec/0.2.0/ucspec.exe` に配置し、成功後にだけ `.ucspec-version` を更新します。版固定の差分をGitでレビュー・コミットしてください。共有CLIだけを更新しても、他のプロダクトは自動で更新されません。

`.tools/ucspec/` 配下のCLIに対する直接の自己置換は拒否します。必ず `--project` で製品単位の更新を行ってください。仕様、記述ガイド、JSON Schemaのコピー、モデルデータは更新しません。スキーマの再出力は `schema --out spec/ucspec.schema.json` で明示します。スキーマ版の破壊的移行は初版では自動化していません。

旧版へ戻す場合は `--version <old> --allow-downgrade` を指定します。旧版がローカルに残っていれば、レビューして `.ucspec-version` を旧版に戻す方法も使えます。

## プライベートリポジトリ

公開リポジトリは通常トークンなしで取得できます。プライベートの場合は、そのリポジトリとReleaseを読める `GH_TOKEN` または `GITHUB_TOKEN` を環境変数で渡します。CLIはトークンをファイルやログへ保存しません。CIではSecretsから設定し、仕様データに書かないでください。

新しい端末では `scripts/setup-ucspec.ps1` が固定された版の取得だけを行います。初回リリース前はダウンロードできません。ソースビルドしたCLIをinitで導入してください。

## トラブルシューティング

| 現象 | 確認・対処 |
|---|---|
| 版が一致しない | `.ucspec-version` と `version` を確認。固定版ランチャーを使う |
| 解析未完了 | `limits.paths` を確認。状態の構造や `scope` を見直す。闇雲に上限を増やさない |
| シナリオの手順が不成立 | その時点の末端状態とその祖先にイベントがあるか、アクターが起こせるか、通るディシジョンごとに分岐名を指定したかを確認 |
| 状態の参照が曖昧 | 複数の状態に一致するパスの末尾を書いている。パスを書き足す |
| 起点が到達不能 | ルート状態の開始から usecase.starts の状態へ至る遷移があるか確認 |
| 既存ファイルとの衝突 | `init --dry-run` で対象を確認。手動編集を自動破棄しない |
| 更新HTTPエラー | Release公開状況、タグ、owner/repo、権限、レート制限を確認 |
| チェックサム不一致 | インストールしない。配布側のZIP/checksumsを確認 |
| 更新時のアクセス拒否 | 書込権限、別プロセス、ウイルス対策ソフトを確認。管理者権限を前提にしない |
| `.update.lock` が残る | 更新プロセスが終了したことを確認してから、そのロックだけを手動削除 |
| 置換中の電源断 | プロセス停止後、旧版 `.previous` から手動復元。電源断時の完全トランザクションは保証しない |
| Windowsが未署名警告を出す | 発行元・入手元・ハッシュを確認。組織のセキュリティ方針に従う |

既存ファイルのデータを失う可能性がある操作を、問題解消のために自動実行することはありません。
