# オンボーディング

## 1. 役割を理解する

ucspecは、顧客との接点を持つ開発者のユースケース駆動開発を支援します。利用者の目的とシナリオの期待結果を明確にし、実装・テストの根拠を構造化仕様として残します。E2Eテストの生成・実行・対応付けと、顧客との合意状態の管理はスコープ外です。

人: 目的、期待結果、禁止事項、未網羅ケースを追加する意味を判断します。
AI: 合意した目的に沿って共有モデル・参照・シナリオを編集し、CLIを実行します。
CLI: 同じ入力から同じ検査結果を算出します。意味のあるシナリオかどうかは自動承認しません。

## 2. サンプルを読む

同梱サンプルの内容と参考アプリの操作は [examples/customer-crud](../examples/customer-crud/README.md) を参照してください。参考アプリは、CLIの検査がアプリとの適合を保証するものではありません。

ソースビルドはREADMEの `scripts/build.ps1` を使用します。成功後に次を実行します。

```powershell
.\dist\ucspec.exe build --project examples/customer-crud/spec/project.json
```

`artifacts/ucspec/index.html` はサンプルプロダクトのディレクトリに作成されます。全体図の開始点から、パッケージ、ユースケース、シナリオ、未網羅経路の順に見てください。遷移が全網羅でも、遷移ペアや上限付き完了パスには未網羅が残ることがあります。シナリオを選び、目的・期待する結果と、図で強調される経路を確認してください。

## 3. 自分のプロダクトを初期化する

```powershell
C:\Tools\ucspec\ucspec.exe init --dir C:\work\my-product --name MyProduct --dry-run
C:\Tools\ucspec\ucspec.exe init --dir C:\work\my-product --name MyProduct
```

`create` / `unchanged` / `conflict` の一覧を確認します。conflictがある場合、既存ファイルを手で確認してから構成を調整してください。強制上書きはありません。

初期化時は説明用のサンプル仕様が入り、`.agents/skills/ucspec-authoring/SKILL.md` も配置されます。プロダクト固有の仕様を推測して生成するわけではありません。最初の目的を決め、サンプルを自分の仕様へ置き換えます。

## 4. 最初のユースケースを作る

最初から全画面を洗い出す必要はありません。目的・成功/中止の終わり方・アクターを定め、必要な状態・イベント・ディシジョンを共通モデルへ追加します。ユースケースの `scope`、`starts`、`ends` は、シナリオを書く前に独立に定義します。要素の関係は [状態定義モデル](model.html) を参照してください。

各シナリオには `goal`（確かめたい利用者の目的）と `expectedOutcome`（業務上の期待結果）を記述し、手順をイベント名と通る分岐名で書きます。「完了画面が表示される」だけでなく、何の目的がどう達成されたかを記述します。

`spec/AGENTS.md` にプロダクト固有の約束を追記します。たとえば「編集/削除は閲覧を経由する」「削除前に確認する」「編集できないアクターには編集イベントを許さない」です。

AIに渡す作業例:

> $ucspec-authoring を使い、顧客情報を最新の内容へ更新する目的の仕様を記述してください。既存の検索・閲覧のイベントを再利用し、更新成功・編集取消の目的と期待結果、編集できないアクターの拒否を定義してください。システムエラーは既存の共通ルールに従ってください。check/buildを実行し、未網羅の業務上の意味、必要な設計要求、変更影響を報告してください。検査閾値、`scope`、`ends`、回帰は緩めないでください。

## 5. レビューとCIへつなぐ

```powershell
.\scripts\ucspec.ps1 build
Copy-Item .\artifacts\ucspec\report.json .\baseline.json
# 仕様を編集
.\scripts\ucspec.ps1 build --baseline baseline.json
```

確認するものは「モデル差分」「影響するユースケース」「無効になったシナリオ」「増えた未網羅項目」「回帰・閾値の変更」です。生成図の見た目だけではレビューしません。

未網羅項目は [6指標の評価方針](coverage.md) に沿って確認し、追加シナリオが必要か、既存シナリオで代表できるか、禁止すべきかを判断します。`coverageReviews` へ理由と必要な設計要求を記録しても、生の網羅率は変わりません。仕様変更で「再評価が必要」になった記録は根拠から見直します。形式は [記述ガイド](authoring.md) を参照してください。

新しい開発環境では `scripts/setup-ucspec.ps1` で指定版だけを取得し、`scripts/ucspec.ps1 check` をCIで実行します。リリースがまだない初期開発では、ソースから作った同版CLIを `init` でコピーしてください。
