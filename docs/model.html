状態定義ファイルの要素と関係

状態・イベント・ディシジョン・分岐の構造だけで仕様を書きます。変数や条件式などのデータの層は持たず、イベント・開始・分岐が共通の「遷移」を継承します。図の各箱が状態定義ファイルに書く要素、ひし形付きの線が「その中に書く」所有関係です。書き方の詳細は 記述ガイド を参照してください。

クラス図

状態・イベント ディシジョン・分岐 ファイル・アクター ◆ コンポジション（中に書く）　→ 関連（名称で参照）　▷ 汎化（継承）

［0..*］などは個数、« » は制約です。点線で結んだ {xor} は、結ばれた2本の関係のうち多くとも一方だけを持つことを表します。イベント・開始・分岐は、どれも抽象クラス「遷移」を継承し、アクションと「行き先の状態」または「ディシジョン」を持ちます。どちらも持たない遷移は、その状態に留まります。ただし開始は、どちらか一方を必ず持ちます。

各要素の属性と規則

名前を持つ要素（アクター、状態、イベント、分岐）の名前は、そのまま識別子です。日本語を使えます。名前には / : > ? [ ] を含められず、前後に空白を置けません。製品のCLIは、同じ並びの中でNFKC正規化すると同じになる名前（全角・半角の違いなど）を表記ゆれとして拒否します。

状態定義ファイル

仕様を書く1つのJSONまたはYAMLファイルです。schemaVersion に "1" を書きます。ファイルの最上位は名前のないルート状態で、最上位に書く start、events、states はルート状態に属します。複数のファイルは1つのルート状態にまとまり、ルート状態の start は全ファイルを通じてちょうど1つ書きます。同じ形式のファイルに、アクター、ユースケース、回帰、共通ルールも書けます。

アクター

属性JSON規則
名称actors のキー全ファイルを通じて一意
説明description任意

ファイルの最上位に書きます。イベントの actors とユースケースの actor が名称で参照します。役割や権限の違いは、イベントを起こせるアクターで表します。

状態

属性JSON規則
名称親の states のキー同じ親の中で一意。ルート状態からのパス（顧客管理/顧客編集）で識別
画面screen任意の文字列。図には状態名と違うときだけ表示
配置層layoutLayer任意の非負整数。同じ親の中での図の配置順。検査には影響しない
開始start子状態を持つ状態では必須。子状態を持たない状態には書けない
イベントeventsイベント名から定義へのmap
子状態states子状態を入れ子で書く

子状態を持つ状態へ入ると、開始をたどって子状態を持たない状態（末端状態）まで進みます。末端状態にいる間、その祖先もすべて有効です。状態を参照する箇所には、完全なパスか、1つの状態だけに一致するパスの末尾を書けます。

遷移 «抽象»

属性JSON規則
アクションaction任意。選んだ遷移で行うシステムの振る舞い
行き先の状態to状態の参照。decision とは同時に書けない
ディシジョンdecisionto とは同時に書けない

イベント・開始・分岐に共通する部分です。to を持てばその状態へ入り（子状態を持つ状態なら開始をたどり）、decision を持てば分岐し、どちらも持たなければイベントが起きた末端状態に留まります。留まるときは退場・再入場や開始への入り直しは起こりません。

イベント

属性JSON規則
名称状態の events のキー状態の中で一意
アクターactors必須。1つ以上のアクターの名称
通常表示defaultVisible任意。true なら通常図に表示。検査には影響しない
遷移の属性action, to, decision遷移を継承

イベントは状態の中に書き、そのまま遷移になります。子状態は親のイベントを引き継ぎ、どの子状態にいても親のイベントを起こせます。末端に近い状態に同名のイベントがあれば、そちらが優先します。ルート状態に書いたイベントはすべての状態で有効です。

開始

状態の start に書く遷移です。遷移の属性を継承し、行き先の状態かディシジョンを必ず持ちます（留まることはできません）。開始とその分岐の行き先は、その状態の内側の状態でなければなりません。ルート状態の開始はシステム全体の開始で、どの状態を行き先にしてもかまいません。状態へ入ると自動的に進み、利用者が起こすものではありません。

ディシジョン

属性JSON規則
表示名label任意。図に表示する。重複してよい
分岐branches必須。分岐名から分岐へのmap。2つ以上

遷移の後にどの分岐へ進むかを表します。独自の識別子を持たず、それを持つイベント・開始・分岐に属します。図では、それを持つ遷移の矢印が入る菱形で表示します。

分岐

属性JSON規則
名称branches のキー同じディシジョンの中で一意
遷移の属性action, to, decision遷移を継承

分岐は条件式を持たず、名前だけを持ちます。どの分岐を通るかはシナリオが分岐名で指定します。分岐の後にさらに分岐するときは decision を入れ子で書きます。分岐の木は合流も循環もしません。行き先を持たない分岐は、イベントが起きた末端状態へ戻ります。開始の分岐は留まれません。

識別のしかた

要素識別子例
アクター名称。全ファイルを通じて一意編集担当者
状態ルート状態からのパス。名称は同じ親の中で一意。ルート状態は名前を持たない顧客管理/顧客編集
イベント状態:イベント。別の状態の同名イベントは別物。ルート状態のイベントは :イベント顧客管理/顧客編集:更新
開始状態:[開始]。ルート状態の開始は :[開始]顧客管理:[開始]
ディシジョン独自の識別子を持たない。それを持つイベント・開始・分岐に属する表示名「顧客の有無」は重複してよい
分岐持ち主の遷移に >分岐名 を続けた並び顧客管理/顧客編集:更新>顧客なし

ユースケース、シナリオ、網羅率、レポートは、アクター・状態・イベント・分岐をこの識別子で参照します。ユースケースの scope はイベントを、ends はイベントまたは分岐を参照します。状態の部分には、1つの状態だけに一致するパスの末尾（顧客編集:更新）も書けます。

記述例

ファイルの最上位は名前のないルート状態で、その start がシステム全体の開始です。子状態は親の states の中に書きます。顧客編集で「更新」すると、顧客を更新してから顧客の有無で分岐します。分岐は条件式ではなく名前だけを持ちます。

{
  "schemaVersion": "1",
  "start": { "to": "顧客管理" },
  "actors": {
    "担当者": { "description": "顧客情報を検索・閲覧する" },
    "編集担当者": { "description": "顧客情報を編集・削除もできる" }
  },
  "states": {
    "顧客管理": {
      "start": { "to": "顧客検索" },
      "states": {
        "顧客検索": { … },
        "顧客閲覧": { … },
        "顧客編集": {
          "events": {
            "更新": {
              "actors": ["編集担当者"],
              "action": "顧客を更新する",
              "decision": {
                "label": "顧客の有無",
                "branches": {
                  "顧客あり": { "action": "顧客を表示する",
                                "to": "顧客閲覧" },
                  "顧客なし": { "action": "アラートを表示する",
                                "to": "顧客検索" }
                }
              }
            },
            "取消": { "actors": ["編集担当者"],
                      "to": "顧客閲覧" }
          }
        }
      }
    }
  }
}

分岐の後にさらに分岐する場合は、分岐の行き先に次のディシジョンを書きます。

"branches": {
  "顧客なし": { "action": "アラートを表示する",
                "to": "顧客検索" },
  "顧客あり": {
    "decision": {
      "label": "競合の有無",
      "branches": {
        "競合なし": { "action": "顧客を表示する",
                      "to": "顧客閲覧" },
        "競合あり": { "action": "競合を表示する",
                      "to": "顧客編集" }
      }
    }
  }
}

行き先を持たない分岐は、イベントを起こした状態に留まります。

"削除": {
  "actors": ["編集担当者"],
  "decision": {
    "label": "削除確認",
    "branches": {
      "はい": { "action": "顧客を削除する",
                "to": "顧客検索" },
      "いいえ": {}
    }
  }
}

シナリオの手順は、イベント名と、通る分岐名の並びで書きます。

"steps": [
  { "event": "検索", "branches": ["1件以上"] },
  { "event": "閲覧", "branches": ["顧客あり"] },
  { "event": "編集" },
  { "event": "更新", "branches": ["顧客なし"] }
]

検査で確かめること

  • 構造が正しいか。名前の規則と表記ゆれ、参照先の状態があり一意に決まること、子を持つ状態（ルート状態を含む）がそれぞれ開始を持つこと、開始の行き先がその状態の内側にあること、ディシジョンに分岐が2つ以上あること。到達できない状態や、上書きされて一度も起きないイベントは警告します。
  • シナリオがたどれるか。各手順のイベントがその時点の状態で受け付けられ、指定した分岐名がそのイベントの先に実在すること。ユースケースのシナリオは、scope のイベントだけを使い、ends のいずれかを通って終わること。
  • アクターが起こせるか。シナリオの手順に、アクターが起こせないイベントが含まれていないこと。「担当者は編集できない」のような権限は、回帰の拒否の手順（"reject": true）で確かめます。
  • ユースケースを終えられるか。ユースケースの各開始から、scope のイベントだけで ends に到達できること。
  • 網羅率。末端状態・複合状態・遷移（イベントと分岐）・連続する2遷移・経路を、シナリオがどれだけ通っているか。

データの中身と業務の論理（顧客が存在するかがどう決まるか、など）は検査しません。それは実装とそのテストが受け持ちます。
