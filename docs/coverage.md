# 網羅率と保証範囲

このツールが計算するのは登録された有効なシナリオの**定義網羅率**です。対象アプリのコードを実行したカバレッジではありません。

網羅率はユースケースごとに、そのユースケースの制御グラフに対して計算します。制御グラフは、`starts` から、ユースケースのアクターが起こせる `scope` のイベントとその分岐だけで到達できる構成（有効な末端状態、または解決中のディシジョン）と、その間の遷移です。`ends` のいずれかを通り、ディシジョンを抜けて末端状態に戻った時点を完了とします。

| JSON上の指標 | 分母 | 網羅済みとする条件 |
|---|---|---|
| states | 制御グラフで到達できる末端状態 | 有効なシナリオの開始時または遷移後に到達 |
| compositeStates | 上記の末端状態の親として有効になる複合状態 | 有効なシナリオでその親が有効になる |
| transitions | `scope` のイベント、その下の分岐、グラフが通る開始の分岐のうち、完了する経路に含められるもの | 有効なシナリオに一度以上出現 |
| pairs | 上記の遷移どうしで、連続して起こり得る2遷移の組のうち、完了する経路に含められるもの | 同じ順で連続して出現 |
| primePaths | 他の単純パスの真部分経路ではない単純パスのうち、完了する経路に含められるもの | シナリオの連続した部分経路として出現 |
| boundedPaths | steps上限内で開始から完了まで進む遷移ID列 | 完全なシナリオ列が一致 |

遷移はイベントと分岐です。網羅率の項目IDは `顧客管理/顧客編集:更新` や `顧客管理/顧客編集:更新>顧客なし` のような遷移IDです。ディシジョンを持つイベントでは、イベント自体と各分岐をそれぞれ一つの遷移として数えます。行き先を持たず状態に留まるイベント・分岐も、通常の遷移として同じ指標の分母に含めます。開始の遷移自体は数えませんが、開始のディシジョンの分岐は数えます。ディシジョンは状態ではないため、`states`/`compositeStates` の分母に入りません。

状態の`layoutLayer`、`defaultVisible`、黒丸の位置、`DOWN`方向、横位置、間隔、矢印の配置は、制御グラフ、`scope`、各網羅率の分母・分子、解析完了状態を変えません。

プライムパスは構成を頂点とする単純パスから作ります。最初の頂点に戻って閉じる閉路は許します。閉路の回転も別経路として扱います。無制限の反復回数のすべてを要求するものではありません。

部分状態への到達は親状態への到達にも数えますが、兄弟の部分状態は網羅済みにしません。一般例として、複合状態「申請」に子状態「下書き」と「確認待ち」がある場合、下書きだけを通るシナリオは申請と下書きを網羅しますが、確認待ちは未網羅です。親に定義したイベントは複数の子から起こせても、transitionsでは遷移IDを一度だけ数えます。子ごとの違いは連続遷移や経路の指標で確認します。描画用の開始記号・開始の矢印は網羅率に加算しません。

`transitions/pairs/primePaths` の候補のうち、それを含んでユースケースの完了まで進む経路が制御グラフに存在しないものは、分母に数えず `infeasible`（HTMLでは「ユースケースの終了に到達できないため除外した経路」）に記載します。完了できない経路があること自体を無条件で正しいとは扱いません。各ユースケース開始点の完了可能性検査の結果と併せて確認してください。

## 境界と不完全な解析

`limits.paths` は制御グラフの構成数と、経路の列挙・成立性探索の作業量の上限です。`steps` はboundedPathsの最大遷移数です。探索上限到達は `complete:false` とします。

未完了の分母は確定値ではありません。%を表示しても合格判定には使いません。到達不能を証明できない候補を勝手に分母から除外しません。分母0は%なし（N/A）です。

boundedPathsは遷移ID列で重複をまとめます。開始から終了しない有限prefixや無限実行の全網羅ではありません。

仕様はデータを持たないため、データの値の組み合わせや条件の真偽に関する網羅率はありません。どの分岐を通るかを決める業務の論理は、実装とそのテストで確認します。

## シナリオと探索の独立性

シナリオが一つもなくても `scope`/`starts`/`ends` から検査対象を作ります。有効でないシナリオを分子に含めません。回帰は定義網羅率へ加算せず、独立した合否として表示します。

シナリオの自動追加や期待結果の自動承認はありません。候補を追加する場合は名前・目的・期待結果を確認します。

## 未網羅項目のレビュー方針

経路が違うことと、別の目的・期待結果を持つシナリオが必要なことは一致しません。顧客との接点を持つ開発者が、次の粒度で不足を評価します。これはレビューの指針であり、検査閾値を変更する規則ではありません。

| 指標 | 評価・管理する粒度 |
|---|---|
| states | 未到達の各末端状態を評価し、その利用状況や結果の不足を確認する |
| compositeStates | 未到達の各複合状態を評価する。親への到達と各子状態の通過は分けて確認する |
| transitions | 未網羅の各イベント・分岐を原則評価し、基本的な振る舞いや結果の不足を確認する |
| pairs | 前の操作が次の操作の意味に影響する組み合わせを重点的に評価する |
| primePaths | 既存シナリオと異なる目的・期待結果・状態履歴を持つ経路を評価する |
| boundedPaths | 探索に使い、全経路の個別判定を必須にしない。反復や順序の違いに意味がある場合に管理する |

ユースケースの `coverageReviews` に、シナリオ追加が必要（addScenario）、既存シナリオで代表（represented）、禁止すべき振る舞い（forbidden）の判断と理由を記録します。複数の未網羅項目を一つの判断へまとめられます。現時点の評価がない項目は未評価のまま表示します。記法と変更後の再評価については記述ガイドの「未網羅項目の評価記録」を参照してください。

一度と二度の再試行を同じシナリオで代表させる場合、入力保持、回数によらない振る舞い、重複処理の防止など、代表させる前提を `architectureRequirements` に記録します。回数制限や回数に応じた待ち時間が仕様にあるなら、その境界には別の評価が必要です。前提の記録は設計・実装の適合を証明しません。

評価記録は分母・分子・閾値判定から独立しています。評価済みであっても未網羅の経路は未網羅として残ります。禁止する記録を追加しても、その経路をモデルから削除したことにはなりません。探索が未完了なら評価できた項目があっても全体を検証済みにしません。
